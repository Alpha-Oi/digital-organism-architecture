# Профиль внедрения: Kubernetes и потоки событий

**Статус:** Informative. Профиль не вводит требований и не меняет claim: при противоречии действуют нормативные документы ([`docs/TERMINOLOGY.md`](../docs/TERMINOLOGY.md), раздел 3). Машиночитаемая форма таблицы требований — [`kubernetes-event-streaming.yaml`](kubernetes-event-streaming.yaml). Профиль не требует конкретного продукта: вместо Kubernetes подойдёт совместимый оркестратор, вместо конкретного брокера — любая система потоков с теми же свойствами.

## Простыми словами

В этой архитектуре система состоит из множества небольших сервисов, которые работают в контейнерах под управлением оркестратора (Kubernetes) и общаются через поток событий. Это естественная основа для DOA: каждый контейнер — отдельная клетка, оркестратор умеет останавливать и заменять клетки, а брокер событий играет роль кровеносной системы. Профиль показывает, как выполнить требования DOA, включая распределённые (профиль Distributed), и где платформа сама ничего не гарантирует. Главная трудность в том, что кластер — это общий домен отказа: пока вы работаете в одном кластере, его управляющая часть остаётся общей судьбой всех сервисов.

## Термины профиля

| Термин | Что это |
|---|---|
| Pod | минимальная единица запуска в Kubernetes: один или несколько контейнеров, которые работают вместе. В профиле pod — клетка |
| Namespace | логическая группа объектов кластера; на неё навешивают права, квоты и сетевые правила |
| ServiceAccount | идентичность pod внутри кластера, к которой привязаны права и токен |
| NetworkPolicy | сетевое правило: кто с кем может общаться. Работает, только если сетевой плагин (CNI) его выполняет |
| Admission-политика | проверка, которая срабатывает при создании объекта в кластере и может его отклонить |
| GitOps | подход, при котором желаемое состояние лежит в репозитории, а контроллер приводит кластер в соответствие с ним |
| Lease | объект с ограниченным сроком действия: право существовать или быть лидером, которое нужно продлевать |
| Control plane | управляющая часть кластера, которая принимает решения о запуске, остановке и правах |
| Брокер событий | сервис, в котором сообщения хранятся в виде журнала и читаются потребителями |
| Партиция | часть темы в брокере; порядок сообщений гарантируется только внутри неё |
| Fencing token (epoch) | монотонно растущий номер: ресурс отвергает команды с меньшим номером, поэтому «старый лидер» не может навредить |
| Зона | физически независимая область датацентра или облака |

## Когда выбирать и когда нет

| Подходит | Не подходит |
|---|---|
| система уже построена из сервисов или должна масштабироваться на несколько узлов и зон | достаточно одного приложения на одном сервере (см. [профиль модульного монолита](modular-monolith.md)) |
| нужен профиль Distributed: независимые домены отказа, кворум, failover | у команды нет опыта эксплуатации Kubernetes и потоков событий |
| сервисы можно изолировать как отдельные pods | система управляет физическим оборудованием, и аварийная остановка зависит от сети |
| нужны распределённые события с доказуемой семантикой доставки | требуется независимость от отказа всего кластера, а кластер один |

## Как DOA выглядит в Kubernetes

| Понятие DOA | Что это в Kubernetes и потоках событий |
|---|---|
| Организм | набор namespaces с сервисами плюс внешние службы: брокер событий, хранилище audit, хранилище genome, identity authority. Они входят в границу организма |
| Орган | сервис (Deployment) с SLO, владельцем и публичным интерфейсом |
| Ткань | набор однотипных реплик (Deployment или StatefulSet) |
| Клетка | pod: у него своя identity, лимиты ресурсов, сетевые правила и lease. Несколько агентов в одном pod — это одна клетка; если по замыслу агенты — клетки, каждому нужен свой pod |
| Геном | подписанный пакет манифестов в репозитории (GitOps) |
| Эпигеном | подписанные манифесты со сроком действия, которые контроллер удаляет по TTL |
| Циркуляция | брокер событий с `EventEnvelope` плюс вызовы между сервисами по mTLS |
| Мембрана | шлюзы входа и выхода и политика «запрещено всё, что не разрешено» в namespace |
| Иммунная система | контроллер `immune` и независимые от приложения механизмы изоляции: сетевая политика, отзыв токенов, удаление pod |
| Идентичность | workload identity на каждый pod, выдаёт identity authority |
| Метаболизм | квоты ресурсов, классы приоритета, бюджет, который резервируется до запуска |
| Admission и lease controller | admission-политики плюс объекты Lease для клеток |

## Главный риск: общий кластер

Pod удобен как клетка, но кластер как целое остаётся общим. Это нужно знать до начала внедрения.

| Что общее | Чем грозит | Как компенсировать | Что остаётся |
|---|---|---|---|
| control plane кластера | при его отказе нельзя запускать, останавливать и лишать прав pods; уже работающие pods продолжают работать | короткие TTL токенов, самозавершение по потере lease, независимый механизм изоляции | один кластер — один домен control plane |
| узел и ядро | сбой узла или побег из контейнера затрагивает все pods на нём | anti-affinity, отдельные пулы узлов, песочницы для недоверенного кода | pods на одном узле делят ядро |
| права администратора кластера | компрометация оператора с широкими правами означает компрометацию всего | минимум прав, разделение ролей, аудит операторов | доверенная база кластера |
| брокер событий | отказ брокера останавливает циркуляцию; общая тема — общая судьба | отдельные темы и ресурсы для vital flow, настройка кворума | брокер остаётся общей зависимостью |
| реестр образов и сеть | недоступность или подмена образов, сетевые отказы | подпись и проверка digest, кэш образов, сетевые политики | зависимость от реестра при запуске |

## Что можно заявить

- **Core:** по оценке автора профиля (не проверено на реальной системе) достижим: pod естественно играет роль клетки, а оркестратор умеет останавливать и заменять её без кооперации. Пределы связаны с общим control plane и общими узлами.
- **Distributed:** по оценке автора профиля достижим при размещении критических органов в разных зонах, кворуме и fencing по epoch (`REQ-DIST-03`, `REQ-DIST-04`). Независимость от отказа всего кластера требует нескольких кластеров; профиль это не оценивает.
- **Adaptive:** применим: границы обучения в genome, изменения через change protocol и progressive delivery.
- **Embodied:** для контура безопасности не рекомендуется. Аварийная остановка и ограничители не должны зависеть от сетевого control plane (`REQ-EMB-02`). Kubernetes можно использовать на верхних уровнях; профиль для edge и робототехники запланирован.
- **Conditional:** проще всего запретить reproduction, federation и horizontal transfer и проверить запрет. Федерация между кластерами возможна только по treaty.

## Состав приложения

| Где | Что |
|---|---|
| Внутри кластера (клетки и органы) | сервисы организма, шлюзы входа и выхода, контроллеры (`immune`, жизненного цикла, учёта бюджета), memory gateway, adapter модели |
| В отдельных namespaces или пулах | symbionts: сторонние инструменты и плагины, недоверенный код |
| Вне кластера, но внутри границы организма | хранилище audit, репозиторий genome и ключи подписи, резервные копии и seed, identity authority, tombstone registry, часть брокера событий при внешнем размещении |

## Как проверять

Kit ([`docs/VERIFICATION_KIT.md`](../docs/VERIFICATION_KIT.md)) применяется без изменений. Для Kubernetes важно следующее:

- В `FS-CELL-01` останавливайте pod без мягкого завершения и проверяйте, что fencing, отзыв токенов и замена выполнил контроллер, а не сам pod.
- В `FS-CELL-03` проверяйте изоляцию без кооперации: сетевая политика, отзыв токена и удаление pod. Убедитесь, что сетевой плагин (CNI) действительно применяет политику.
- Сценарий `FS-CIRC-01` (разделение сети) выполняйте между зонами и вокруг брокера: проверяйте epoch, fencing и отсутствие конфликтующих побочных эффектов.
- В `FS-CIRC-02` нагружайте брокер и проверяйте, что vital flow на отдельных темах укладывается в допуск.
- В `FS-CIRC-03` смещайте часы узла: проверьте сроки токенов, lease и поздние события.
- Отдельно смоделируйте недоступность control plane: уже работающие pods должны завершиться или потерять доступ по истечении токенов.
- В `FS-ORG-01` восстанавливайте кластер из seed в другом домене и перевыпускайте все токены и сертификаты.
- Средство инъекции отказов выберите сами; профиль его не предписывает. Запускайте только в изолированной среде.

## Порядок внедрения

1. Объявите границу организма и failure domains: namespace, пул узлов, зона, кластер.
2. Определите клетки (pods) и органы (сервисы), опишите интерфейсы и владельцев.
3. Оформите подписанный genome в репозитории и включите проверку подписи и digest при создании объектов.
4. Введите workload identity, короткоживущие grants и минимальные права.
5. Закройте сеть: запрет по умолчанию, шлюзы входа и выхода, проверка применения политики.
6. Опишите события: `EventEnvelope`, реестр схем, семантика доставки, ключи партиций, TTL, отдельные темы для vital flow.
7. Разместите критические органы по зонам, настройте кворум, epoch и fencing, объявите источник времени.
8. Вынесите за пределы кластера audit, seed, резервные копии и корень доверия.
9. Прогоните Verification Kit в изолированной среде и оформите claim с честными статусами.

## Другие профили DOA

Профиль внедрения не заменяет профили соответствия (Core, Distributed, Adaptive, Embodied, Conditional); он описывает один из способов выполнить их требования. Профиль для edge и робототехники и профиль для изолированных сетей запланированы в [`ROADMAP.md`](../ROADMAP.md).

## Ограничения профиля

- Профиль написан без независимой реализации: ни одна система не построена и не проверена по нему, поэтому предложенные способы могут потребовать errata.
- Утверждения о возможностях Kubernetes и систем потоков записаны в общем виде и не сверялись с документацией конкретных версий. Перед внедрением сверьте их с документацией своих продуктов.
- Профиль не заменяет вашу модель угроз ([шаблон](../templates/DOA_THREAT_MODEL.md)) и отраслевые требования безопасности.
- Выбор технологий (оркестратор, брокер, сетевой плагин) профиль намеренно не делает.
